## 1. What M5 was for

M0–M4 built the platform, the deterministic exchange core, the futures and
replay stack, the participant pipeline and the first real strategy. What it did
**not** have was a risk engine. `cpp/participant/risk` was an empty
`.gitkeep` directory, `python/validation` did not exist, and every risk verdict
the system had ever produced came from `AlwaysApproveRiskGate` — a test double
(ADR-0023). The mandatory risk seam existed in the OMS, but nothing enforced
anything through it.

M5 makes that seam real in both directions:

- **Risk (AEGIS-120–138).** An independent `risk::RiskEngine` that a strategy
  cannot bypass, with eighteen enforced controls, an auditable decision record
  per proposal, and portfolio-level analytics.
- **Validation (AEGIS-139–155).** An anti-overfitting framework whose job is to
  decide whether a research result may be *believed* — partitioning, walk-forward,
  stability, sensitivity, resampling, baselines, leakage detection and a formal
  rejection verdict.

It also discharges the three inherited obligations dated M5: **AEGIS-062**,
**AEGIS-063** and **AEGIS-238**.

## 3. Risk architecture

`configs/architecture_rules.yaml` already declared that
`cpp-participant-oms` may depend on `cpp-participant-risk`. That single fact
determined the whole design: **`risk` cannot depend on `oms`**, or the layer DAG
would cycle. So the risk layer implements no OMS interface. It defines its own
vocabulary and owns plain-old-data views (`MarketQuote`, `PositionView`) that the
composition root populates; the `oms::RiskGate` adapter lives in
`cpp/participant/app/risk_engine_gate.cpp`, the only layer permitted to see
strategy, risk, OMS and portfolio at once. **No file under
`cpp/participant/oms/` was modified in M5.** M5 needed exactly one new
dependency edge: `cpp-participant-app += cpp-participant-risk`.

```
market data → FeedHandler → BookBuilder(near/far) → CalendarSpreadStrategy
                                                      │  proposal only
                                                      ▼
                      [app]   RiskEngineGate : oms::RiskGate
                                                      │  NewOrderCommand → risk::OrderRequest
                                                      ▼
                      [risk]  RiskEngine::decide() ── audit ──▶ RiskAuditLog
                                                      │  approve / resize / reject + reason code
                                                      ▼
                      [oms]   OrderManager ── reject ─▶ adapter NEVER called
                                                      │
                                                      ▼
                              ExecutionAdapter → real M1 ExchangeNode (tests) / immediate fill (CLI)
                                                      │  fills
                                                      ▼
                                                  Portfolio → PortfolioRisk analytics
```

Beyond the seam itself, the properties that took the most work to get right —
each of them the subject of a repair round during closure, and each now pinned
by its own tests:

- **Two entry points, one enforcement point.** `evaluate()` is pure and used for
  the proposal-wide atomicity pre-check; `decide()` is the mutating, enforcing
  call reached only through the OMS seam. A spread with one rejected leg submits
  **neither** leg — a lone leg is an unhedged position the strategy never proposed.
- **Final-overlay proposal evaluation.** Cumulative limits are checked against the
  proposal's final net projected state, and revalidated atomically at commit, so an
  out-of-band exposure change between evaluation and commit cannot slip through.
- **Commit-time reservations with exact `PendingLeg` identity.** A risk-approved,
  not-yet-terminal order reserves exposure; the reservation is keyed to the exact
  leg identity, so an identity or economics mismatch is rejected and releases what
  it reserved.
- **Proposal-wide release authorization epoch.** Releases are authorized per
  proposal epoch, so a stale release cannot free a reservation belonging to a
  later proposal.
- **API identity isolation and positive-quantity invariants.** A malformed request
  quantity and a malformed *configured* limit are both refused, and
  `check_approved_quantity_postcondition` defends the same hazard for a
  programmatically constructed config that bypasses the loader.

The boundary this does **not** claim is stated in §9.

| 128 | Message-rate limits | Order and cancel windows on the injected virtual clock, never wall clock |
| 129 | Margin availability | Documented simplified initial-margin model; explicitly **not** SPAN |
| 130 | Max leverage | Gross notional / equity, including documented zero-equity behaviour |
| 131 | Daily loss limit | **Latched**: one trip event ever, then `kTradingHalted` — the frozen "exactly once" |
| 132 | Max drawdown | Equity high-water mark via M3's `DrawdownTracker`, same latch |
| 133 | Volatility reduction | Deterministic integer resize with an explicit rounding rule, plus a hard-reject multiple |
| 134 | Concentration / correlation | Config-supplied correlation matrix, never estimated in the decision path |
| 135 | Kill switches | Strategy-level and global, **idempotent**; cancels live orders, blocks new ones |
| 136 | Connectivity loss | Distinct feed / exchange / broker signals, each with a configured response |

**The property that matters most, stated as a test:** in every reject scenario the
execution adapter's submit count is `0`, the real `ExchangeNode` reports **no order
at all**, and the portfolio is identical to its pre-proposal state. A rejection is
enforcement, never a post-hoc report.

## 6. Validation and anti-overfitting

`python/research` owns *how the strategy behaves*. `python/validation` owns
*whether a research result may be believed*. The two are separate packages on
purpose.

### The partition, and why it is the centrepiece

`configs/validation/partitions.yaml` is the **sole runtime source** of the split,
read through `load_partition_boundaries()`. Over the 120-day series it yields
**train = 70, validation = 20, test = 30**, chronological, non-overlapping, every
observation assigned exactly once.

Tuning — the AEGIS-142 parameter search — is fed **90 observations
(train + validation only)**. It gets them from `select_non_test_for_tuning()`,
which obtains `TRAIN` and `VALIDATION` through the *same guarded accessor*
`DatasetPartitions.get(..., purpose=TUNING)` that `guard_test_set_access()`
protects. A tuning-purpose request for `TEST` raises `LockedTestPartitionError`.

The distinction that took a repair round to get right: **the test split is
excluded by the data flow itself, not reported as excluded afterward.** The first
full frozen-spec audit found the earlier implementation failing exactly that
test — `partitions.yaml` was never read, the generator hardcoded
`len(dates) * 2 // 3` (an 80/0/40 split contradicting the committed 70/20/30),
and the lock was demonstrated in an isolated `try/except` whose result was
discarded while the stability search still received the full series, test
partition included. That is now fixed at the data-access point, and a test spies
on the real argument the search receives during an actual evidence run rather than
inferring it from artifact counts.

The test partition is **locked, not deleted**: `FINAL_EVALUATION` purposes may
read it where the design permits.

## 7. What the research actually found

The pipeline was built to be capable of rejecting the strategy it was built
around, and on this dataset it does exactly that.

| Subject | Verdict | Triggering criteria |
|---|---|---|
| `calendar_spread_strategy` | **REJECT** | transaction cost unprofitable at the lowest swept cost; bootstrap CI excludes a positive mean |
| `intentionally_weak_concentrated_baseline` | **REJECT** | too few round trips; bootstrap CI excludes a positive mean |
| `random_shuffled_signal_baseline` | **ACCEPT** | none triggered |

Three things are worth stating plainly about this table.

**The main strategy is rejected, and that is the framework working.** AEGIS-155's
frozen acceptance asks that at least one intentionally weak strategy produce a
rejection report. What M5 delivers is stronger: the *primary* strategy is put
through the identical pipeline and fails it, on criteria computed from its own
results against thresholds read from committed config. A validation framework
that could only reject strategies chosen in advance to be rejected would prove
nothing. This one rejects the strategy its authors had every incentive to pass.

**The shuffled baseline's ACCEPT is reported, not hidden.** A random baseline is
not *guaranteed* to be rejected on any particular dataset and seed, and pretending
otherwise would be the fabrication this project forbids. The artifact carries an
explicit `not_evidence_for` note saying so.

**No parameter, threshold, config or seed was tuned to change any of these
verdicts.** When the AEGIS-139 repair correctly restricted the tuning input, the
downstream stability dispersion moved — and the verdicts were kept exactly as the
criteria produced them.

## 8. Observability (AEGIS-238)

Verified **in full at M5**. The owner-authorised M8 fallback was **not used**.

One integration run produces all five metric families, every one non-vacuous:
health (`degraded`, from real rejections — never a blind `healthy` default),
queue depth, dropped/backpressured events, execution latency, and **risk status
decoded from the real `risk::RiskEngine`'s own verdict** via the production
binary rather than fabricated.

The disclosure the owner's authorization required is carried in the artifact
itself: queue depth and dropped events come from the M5 integration harness's
**bounded outbound execution buffer**, and are **not** M8's lock-free queue
implementation (`cpp/queues`, empty and M8-dated). The registered residual's
attribution of queue depth to "M1's bounded queues" was inaccurate as to
milestone, and M5 does not repeat it.

### A regression the matrix caught

The matrix is in this report because it did its job. It found a real defect in
committed code that four review rounds had not: `configs/risk/limits_reject_demo.json`
tightened `order_quantity_limits` to `0` to force a rejection, but a later M5
input-integrity repair had correctly made a non-positive configured cap a
load-time error. The demo binary therefore exited `2` on that config — and the
AEGIS-120 and AEGIS-238 evidence artifacts recorded runs the code at their own
cited commit could no longer produce, because they had been generated from a
build predating the validation.

The fix was config-only. Because the demo strategy proposes exactly one unit and
the cap is compared strictly (`quantity > cap`), no *valid* positive quantity cap
can reject a one-unit order; per-order notional is the narrowest real control
that still rejects the same stream without weakening the invariant or changing
the strategy. The enforcement shape the artifact has always recorded is unchanged
— six output lines, two risk decisions, `final_order_count == 0` — and only the
reason code moved, from `kMaxOrderQuantity` to `kMaxOrderNotional`. AEGIS-121's
own reject-or-resize boundary evidence is untouched: it comes from the C++
boundary tests, not from this demo. Both affected artifacts were regenerated so
that each is now reproducible at the commit it cites.

## 11. Limitations — stated plainly

These are scope statements, not defects, and none of them is weakened anywhere
else in this report.

- **Every price in M5 is synthetic.** The venue `SYNX` does not exist. Validation
  runs on a seeded, documented mean-reverting construction, and the risk demo runs
  on a committed synthetic stream.
- **Two-sided quotes are constructed from daily OHLC/settlement bars**, not
  observed tick data (ADR-0025). M5 changes nothing about this.
- **The matching engine is real; the market data is not.**
- **The margin model is an explicitly documented simplification**, not an exchange
  margin model and not SPAN.
- **Validation fill assumptions are not live fills.** Slippage and fill behaviour
  are swept model assumptions, not measured execution.
- **Risk authorization atomicity is not atomic multi-leg exchange execution.** The
  engine guarantees that a multi-leg proposal is authorized or refused as a unit
  and that reservations are consistent at commit. It does **not** provide atomic
  execution of multiple legs at the venue, which no component in this repository
  offers.
- **No multi-currency market data exists in-repo**; the FX normalisation path is
  exercised against a synthetic fixture, and the scope limit is explicit.
- **No live profitability claim is made.** The strategy's own verdict here is
  REJECT.
- **No production risk adequacy claim is made.** The limit values are deliberately
  small, deterministic and sized for the committed demo.

Non-blocking items observed during audit and carried forward as backlog rather
than M5 failures: routing *all* partition reads (not only tuning) through the
guarded accessor; a provenance note on AEGIS-155's mixed criterion inputs; a
`not_evidence_for` block on AEGIS-142's artifact for consistency with its
siblings.
