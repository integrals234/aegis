## 1. What M4 was for

M0–M3 built the platform, the exchange core, the futures/replay stack and a
full participant pipeline — feed handler, book reconstruction, online
statistics, OMS with a mandatory risk seam, and portfolio accounting. It could
reconstruct a book and manage an order, but it had **no strategy**: nothing
ever decided to trade. `cpp/participant/strategy`, `python/research` and
`python/reports` were empty, which is why AEGIS-004 and AEGIS-024 had carried
open residuals since M0 and M2.

M4 builds the first real one: a calendar-spread strategy that produces
signals from reconstructed market state, routes them through the existing risk
seam and OMS, and settles into the existing portfolio — plus the research and
reports that make its behaviour inspectable.

## 3. The first real strategy path

M4's headline result is that AEGIS now executes a complete
signal → order → fill → P&L path through the real M1–M3 infrastructure. Two
surfaces, both deterministic:

**Demo A — production composition** (`cpp/participant/app`, no exchange
dependency):

```
committed two-leg stream → FeedHandler → BookBuilder (one per leg)
  → CalendarSpreadStrategy → RiskGate seam → OrderManager
  → ExecutionAdapter → Portfolio → P&L
```

```
./build/debug/cpp/participant/app/aegis_participant_run --calendar-spread \
    --stream tests/unit/fixtures/participant/calendar_spread_stream.jsonl
```

Enters a short spread at the third observation (z ≈ 2.121), holds, exits at the
sixth (z ≈ −0.301), finishing flat with realized P&L **−95** on the near leg and
**+65** on the far leg. Byte-identical across repeated runs.

**Demo B — real M1 FIFO matching**
(`tests/cpp/unit/test_calendar_spread_exchange_integration.cpp`):

```
CalendarSpreadStrategy → RiskGate seam → OrderManager
  → TransportExecutionAdapter → InProcessExchangeTransport (tests/ only)
  → real unmodified ExchangeNode → real FIFO matching
  → fills → OrderManager → Portfolio → P&L
```

Both legs fill completely against pre-seeded resting liquidity, the OMS
lifecycle reaches `kFilled` only via the exchange's own
`OrderTerminatedEvent{kFilled}` (never inferred), the portfolio ends short the
near leg and long the far leg, and two independent runs produce identical
results.

- **The strategy emits proposals only.** `CalendarSpreadStrategy` returns

## 5. Data limitation — stated plainly

**Every price in this milestone is synthetic.** `data_samples/` carries sample
bars on the fictional venue `SYNX` (`data_samples/PROVENANCE.yaml`).

**The two-sided quote stream is constructed from daily OHLC/settlement bars,
not observed tick data** (ADR-0025). The demo fixture derives a fixed ±$0.10
quote around each bar's settlement price.

Where this report or the code says a price is **"observed"**, that means only
*read from the committed series* rather than *synthesized by this code*. It
never means real market data.

The far leg's price is observed when the supplied series carries one and
constructed otherwise; every observation records which
(`far_price_observed`, `far_price_provenance`). The committed EQX chain has
bars for one contract only, so the demo path is always the constructed
fallback.

**No claim is made anywhere in M4 about execution quality, fill realism, live
market behaviour, profitability, or generalisation.**

## 6. Methodology

**Term structure (AEGIS-077).** Carry as spread ÷ near price (a documented
simplification ignoring financing/storage, which no frozen requirement asks
this milestone to model), contango/backwardation/flat from the spread's sign,
expiry distance, and roll context. Feature tests use known curve shapes.

**Hedge ratio (AEGIS-078).** Static = OLS far-on-near slope via the
covariance/variance identity, computed from the two-pass textbook definition
(ADR-0022's discipline). Rolling = one estimate per observation from the
`window` observations *strictly before* it. Validated both synthetically
(analytically known slopes) and historically (over the committed EQX bars,
against an expectation derived independently through the additive-basis
decomposition, which the estimator never sees).

**Leakage (AEGIS-080, ADR-0026).** An observation is scored against the window
as it stood *before* it, then joins the window — it never influences its own
normalisation. This holds in the compiled C++ `RollingZScore` (reads moments,
then pushes) and in the Python reference (computes from history, then
appends), and is proven behaviourally: an extreme first observation scores
exactly 0.0 and triggers no action in both.

**Cross-language agreement (AEGIS-080).** `research/signal_reference.py`
recomputes mean and sample variance two-pass over a plain deque — a genuinely
different algorithm from the C++ incremental Welford with reverse-Welford
eviction, not a transliteration. This matters: the M3 closure audit caught a
prior "independent" reference that was a line-for-line copy. The two agree
value-for-value **and** produce identical entry/exit classifications, via the
existing `cpp-bindings → cpp-statistics` edge. No
`cpp-bindings → cpp-participant-strategy` edge was created.

## 7. Stationarity (AEGIS-079)

One documented test — unaugmented **Dickey-Fuller**, constant, no trend —
solved by closed-form OLS with no numpy/scipy/statsmodels dependency (none is
pinned).

Recorded result over the CSX fixture spread series: statistic **0.2109**
against a 5% critical value of **−2.86**, n = 10 → **non-stationary** (the unit
root is *not* rejected). The auditor recomputed the regression independently
and matched exactly.

The report states the chosen test, its null and alternative hypotheses,
parameters, three assumptions (no augmentation lags; asymptotic MacKinnon
critical values not finite-sample adjusted; the DF distribution is not
normal/t) and three caveats — including, explicitly, that this is **a result
over the supplied sample only and not a claim that the spread will remain
stationary in future**.

## 9. Roll-method strategy sensitivity (AEGIS-024) — and its limits

M2 had already compared roll *policies* (dates, adjusted price paths); the M4
residual was attributing those differences to **strategy** outcomes. Both
policies run against identical chain, prices, dates, replay configuration and
far-leg rule, with **every policy's far leg observed**, so roll policy is the
only variable that differs.

| Policy | Contract pairs traded | Position | Realized | Unrealized | Total |
|---|---|---|---|---|---|
| `fixed_100_days` | CSX 2026M/2026U | **long** spread | 0 | +50 | **+50** |
| `volume_crossover` | CSX 2026H/2026M, then 2026M/2026U | **short** spread | 0 | −60 | **−60** |

Roll choice changed the traded contract pair, the signal direction, and the
mark-to-market — a **110** total-P&L difference in opposite directions.

### Limits of this experiment, numerically

The auditor flagged this experiment as statistically thin, and it is. Stated
precisely so it cannot be over-cited:

- **n = 10 observations against `zscore_window = 20`** — the window never
  fills; scores come from an expanding 2–9-point prior window.
- **One entry per policy. Zero exits. Zero completed round trips.**
- **`signal_count_difference: 0`** — the counts are equal; the difference is in
  direction and mark-to-market.
- Realized P&L is **0** for both. The 110 difference is a **single unclosed
  mark-to-market** at the final observation's prices, not a trading result.

**This artifact supports only:** under this fixture, roll policy changed the
traded contract pair, the signal direction and the mark-to-market. **It must
never be cited as evidence that roll choice materially affects P&L in
general.** A substantive sensitivity finding needs a larger fixture built
*before* the comparison is run — not enlarged afterwards, which would be
result-shaping.

## 10. Defects found and fixed during M4

**1. Test-fixture price floor not tick-aligned (Batch 1).** The real-matching
integration test seeded counterparty orders at a price the exchange rejected,
so nothing ever filled and the test silently proved nothing. Fixed, and
explicit acceptance assertions were added on the seed orders so the same class
of bug fails loudly next time.

**2. Mismatched-length `zip` in the stationarity differencing step (Batch 2).**
`strict=True` turned it into an immediate `ValueError` rather than a silently
wrong number. Caught by the first focused test.

**3. Observed far-leg prices were discarded (found at closure review).** The
serious one. `build_calendar_spread_observations` always synthesized the far
price from the additive `ConstructedBasisRule`, even when the supplied series
carried that contract's own observed price. Two consequences: an AEGIS-076
provenance defect, and — because `far − near == basis[index]` under an additive
basis regardless of which contract is front — the spread was **algebraically
invariant to the roll policy**, so AEGIS-024 reported a spurious *zero*
strategy difference. The fix prefers an observed far price when one exists and
records which source was used. This was a provenance correction AEGIS-076
wanted on its own terms; the invariance disappeared as a consequence, and
nothing was tuned to produce a difference.

**Found by the independent audit (all remediated):**

**4. AEGIS-078 had no historical test** — the frozen acceptance names
"synthetic **and** historical", and every test was hand-built literals. Added
two tests over the committed EQX bars with an independently derived
expectation. (My first attempt asserted a slope of exactly 1, which was wrong
because the basis is non-constant; the test caught it and the *expectation* was
corrected rather than the tolerance widened. The committed test now asserts the
basis is non-constant, so it can never silently degrade to the trivial case.)

**5. Falsified input provenance in all three Batch 2 reports** — `INPUT_PATHS`
hardcoded a data file the computation never reads, pinning a SHA-256 for a
non-input. Now names the actual input.

**6. AEGIS-079's report stated a false fact about its own series** — a static
disclosure string claimed the series came from `data_samples` bars plus a
constructed basis; for the recorded run both clauses were false (10/10
observations used observed far prices). The disclosure is now derived from the
result and cannot go stale.

**7. Stale/dirty evidence stamps**, **`active_milestone: "M2"` left in the
status file**, **`strategy_config: {}` in two reports**, and **"real" used for
synthetic bars** — all corrected.
