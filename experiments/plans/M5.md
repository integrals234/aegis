## 6. M5 architecture

`configs/architecture_rules.yaml` (authoritative) already declares:

```
cpp-participant-risk   paths: cpp/participant/risk   from: M5
  may_depend_on: [cpp-common, cpp-events, cpp-participant-strategy, cpp-statistics]
cpp-participant-oms    may_depend_on: [..., cpp-participant-risk]
cpp-participant-app    may_depend_on: [common, events, replay, feed-handler, book-builder,
                                       statistics, strategy, oms, portfolio]     <-- no risk
python-validation      paths: python/validation      from: M5
  may_depend_on: [python-common, python-data, python-futures, python-research]
python-reports         may_depend_on: [..., python-validation]                   <-- already allows it
```

Three consequences drive the whole design:

1. **`cpp-participant-risk` must not depend on the OMS.** `oms → risk` already
   exists, so `risk → oms` would be a cycle. Therefore the risk layer **cannot
   implement `oms::RiskGate` directly**; it defines its own vocabulary, and a
   thin adapter in the composition root implements the seam.
2. **`cpp-participant-risk` must not depend on portfolio or book-builder.**
   `may_depend_on` is exhaustive. Risk therefore owns plain-old-data views
   (`MarketQuote`, `PositionView`) that the composition root populates from
   `BookBuilder::TopOfBook` and `Portfolio`. This is a feature: risk state is
   explicit and snapshot-testable, and the risk engine never reaches into the
   accounting it is judging.
3. **`cpp-participant-app` needs exactly one new edge: `+= cpp-participant-risk`.**
   That is the *only* change to `architecture_rules.yaml` M5 requires, and it
   mirrors M4's single-edge `m4-architecture-transition`.

### The seam, precisely

`RiskGate::decide(...)` is `const` — but `OrderManager` holds a **non-const
`RiskGate&`**, and the adapter holds a **non-const `RiskEngine*`**. Calling a
mutating engine method through a pointer member from a `const` adapter method is
legal and honest (`const` on the adapter means the *adapter* is not mutated; the
engine is injected and owned by the composition root, exactly like
`OrderManager`'s own adapter/gate references). **No file under
`cpp/participant/oms/` is modified in M5.**

```
  market data ──> FeedHandler ──> BookBuilder(near) ─┐
                                  BookBuilder(far) ──┴─> CalendarSpreadStrategy
                                                              │ StrategyProposal (proposal-only)
                                                              v
                              [cpp/participant/app]  RiskEngineGate : oms::RiskGate
                                                              │  (translates NewOrderCommand
                                                              │   -> risk::OrderRequest)
                                                              v
                              [cpp/participant/risk] RiskEngine::decide()  ── audit event ──> RiskAuditLog
                                                              │ Approve / Resize / Reject + reason code
                                                              v
                              [cpp/participant/oms]  OrderManager  --reject--> adapter NEVER called
                                                              │ approve/resize
                                                              v
                                             ExecutionAdapter -> (demo A: immediate fill;
                                                                  demo B: real M1 ExchangeNode in tests/)
                                                              │ fills
                                                              v
                                                          Portfolio ──> PortfolioRisk analytics
                                                              │
                                    app feeds back: on_fill / on_mark / on_market_data / on_connectivity
                                                              └──────────────> RiskEngine state
```

Boundaries preserved: **strategy → proposal → risk → OMS**. No `strategy → OMS`,
no `strategy → exchange`, no gateway, no `validation → trading control`
(validation is offline Python reading committed artifacts only). The
`banned.gateway_header_markers` and `mutable_globals_forbidden_in` rules are
untouched — `cpp-participant-risk` is already in the mutable-globals ban list.

## 7. Risk-engine design

**Files (all new, all inside the M5-allowed `cpp/participant/risk/**`):**
`reason_codes.hpp`, `risk_limits.hpp`, `risk_types.hpp`, `risk_state.{hpp,cpp}`,
`margin_model.{hpp,cpp}`, `risk_engine.{hpp,cpp}`, `risk_audit.{hpp,cpp}`,
`CMakeLists.txt`.

Two entry points, one enforcement point:

* `RiskDecision evaluate(const OrderRequest&) const` — **pure**, no state
  mutation, no audit. Used by the composition root for two-leg *atomicity*
  pre-check (a spread with one leg rejected must submit **neither** leg — a
  lone leg is an unhedged position the strategy never proposed).
* `RiskDecision decide(const OrderRequest&)` — **mutating**: consumes a
  rate-limit token, records the idempotency key, appends **exactly one**
  `RiskDecisionEvent`. Called **only** from `RiskEngineGate::decide` inside the
  OMS seam. This is the enforcement point: a reject means `adapter.submit()` is
  never reached, which `OrderManager` already guarantees.

Every control below is derived from a frozen requirement; nothing is added
because it sounds useful.

mechanism is built (explicit `base_currency`, an FX table, rejection of any
instrument whose currency has no rate) and tested against a synthetic non-USD
fixture; the **absence of real multi-currency market data is stated explicitly**
in `docs/LIMITATIONS.md` and ADR-0028. This pays the frozen "or unsupported
scope is explicit" branch honestly rather than claiming FX support.

## 8. Validation-layer design (`python/validation/`)

**Ownership boundary.** `python/research` owns *how the strategy behaves*
(signals, replay, term structure, roll policy). `python/validation` owns *whether
a research result may be believed* (partitioning, resampling, sensitivity,
baselines, leakage, rejection). `python/reports` owns rendering and provenance
only. `python/attribution` stays empty (M6).

`python-validation` may depend on `python-common`, `python-data`,
`python-futures`, `python-research` — all four already permitted. **No
architecture change.** Design constraint: AEGIS-139's manifest mechanism
**composes** `data.experiment_manifest` rather than editing it, keeping
`python/data/**` out of the diff (it is out of M5 scope).

## 9. Real M5 vertical demo

Extends the M4 real-deal path. **Demo A** (production CLI,
`aegis_participant_run --calendar-spread --risk-config <path>`) and **Demo B**
(test-only harness driving a real, unmodified M1 `ExchangeNode` with real FIFO
matching — the same legal boundary
`test_calendar_spread_exchange_integration.cpp` already uses).

```
Scenario 1 — ALLOW
  stream -> FeedHandler -> BookBuilder x2 -> CalendarSpreadStrategy
        -> RiskEngine.decide()  => kApprove (both legs)
        -> OrderManager.submit_new_order -> adapter.submit()
        -> real ExchangeNode, real FIFO match -> fill
        -> Portfolio: position, realized/unrealized P&L, cash
        -> PortfolioRisk: gross/net exposure, margin, drawdown

Scenario 2 — REJECT (size)
  oversized proposal (quantity above the per-instrument max, resize disabled)
        -> RiskEngine.decide() => kReject / kMaxOrderQuantity
        -> adapter NEVER called; NO order exists at the ExchangeNode

Scenario 3 — REJECT (safety)
  kDelayed fault ages the quote past max_quote_age
        -> kReject / kStaleMarketData ; no order

Scenario 4 — RESIZE
  volatility rises -> kResize ; the order submitted carries the reduced quantity

Scenario 5 — KILL SWITCH
  daily-loss threshold breached -> single trip event -> live orders cancelled
        -> every subsequent proposal rejected kTradingHalted, no second trip event
```

**Exact acceptance assertions:**

1. Two runs of each scenario produce **byte-identical** output lines.
2. Scenario 1: `ExchangeNode` reports a trade at the expected price/quantity; final `Portfolio` position, average price, realized P&L, unrealized P&L and cash equal literal expected values; the risk audit log holds exactly one `kApprove` record per submitted leg.
3. Scenarios 2 and 3: execution-adapter submit count `== 0`; `ExchangeNode` order count unchanged; `Portfolio` state identical to pre-proposal; audit log holds exactly one reject record with the expected reason code.
4. Scenario 4: `TrackedOrder::original_quantity_units` equals the **resized** quantity, not the proposed one.
5. Scenario 5: exactly one trip event; cancel issued for each live order; subsequent submits rejected; a second `trip_*()` call changes nothing.
6. Global invariant across all scenarios: **every order that reached the execution adapter has exactly one approve/resize audit record**, and there exists **no** order at the adapter without one.

## 20. CI performance — actual current behaviour on canonical main

Inspected, not assumed:

**Owner decision (this planning turn): parallelise it, inside M5.**
