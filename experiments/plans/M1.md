## 3. Design decisions (each carried by an ADR; narrowest defensible reading where the spec is silent)

- **No floating point anywhere** in engine state, canonical encodings or snapshots. `cpp/events/envelope.hpp` already forbids it; a `double` price would make byte-identical replay a property of libc.
- **Three separate identifier spaces** — `CommandSequence`, `EventSequence`, `OrderId` — never derived from one another (§4.3).
- **Integer price *units* with a declared `tick_size_units`, integer quantity *units* with a declared `lot_size_units`**, so tick and lot validation are genuine tests rather than tautologies (§4.4).
- **The engine reads no clock.** `ExchangeTime = max(previous_exchange_time, command.event_time)`, derived purely from input. `MonotonicTime` appears only in `bench_main.cpp` and `cpp/common/time.hpp` makes serializing one a compile error.
- **A market order is accepted, never rejected for lack of liquidity.** It passes the same validation matrix as any order; once accepted it emits `kOrderAccepted`, matches what it can, and its unfilled residual never rests — the order is closed with `kOrderTerminated` carrying `TerminationReason::kResidualCanceled`. An **empty book is the same path**: accepted, zero trades, whole quantity terminated as residual. AEGIS-029's frozen text is "execute market orders against available liquidity with explicit residual handling" and nowhere requires rejection, so absent liquidity is an execution outcome, not a validation failure, and there is no `kInsufficientLiquidity` reject reason. One documented policy; no TIF matrix.
- **Modify semantics**: a quantity *decrease* is applied in place and **retains** priority; a quantity *increase* or any price change is **cancel-replace** — the order terminates and a replacement is created with a **new `OrderId`** and a new priority at the tail of its level.
- **No self-trade prevention, no auctions/opening cross, no pro-rata, no multi-threading, no cancel-by-client-order-id.** Recorded in `docs/LIMITATIONS.md`.
- **Domain message vocabulary lives in `cpp/events`**, not in the exchange, so M3's participant can consume exchange events without depending on an exchange type. This is AEGIS-004 made structural.
- **"Expected O(1)" wording.** `configs/claims_policy.yaml` bans "all operations strict O(1)". Documentation says: expected constant-time lookup over a pre-sized index, worst case linear in bucket occupancy; matching is output-sensitive in the number of resting orders consumed.

### 4.2 Wire vocabulary — `cpp/events/exchange_messages.{hpp,cpp}` (layer `cpp-events`)

Permanent `MessageType` numbers in the reserved 1..999 band; `is_known_message_type()` extended and its unit test updated.

Commands: `kNewOrder=1`, `kCancelOrder=2`, `kModifyOrder=3`.
Events: `kOrderAccepted=10`, `kOrderRejected=11`, `kOrderModified=12`, `kOrderReplaced=13`, `kTrade=14`, `kOrderTerminated=15`.

`kOrderModified` is the in-place, priority-retaining quantity decrease. `kOrderReplaced` carries `{old_order_id, new_order_id}` for the cancel-replace path. `kOrderTerminated` carries a `TerminationReason { kFilled, kCanceled, kResidualCanceled, kReplaced }`, so every order's removal has exactly one event and one reason.

Encoding follows the existing canonical rules of [cpp/events/envelope.hpp](cpp/events/envelope.hpp): fixed field order, fixed-width little-endian, length-prefixed strings, no floats, no map iteration order, encoded field by field (never a struct `memcpy`, whose padding is uninitialised).

### 4.3 Identifier spaces — **correction 2**

Three distinct strong types, none convertible to another, each with its own counter, its own serialization slot and its own restore rule.

| | `CommandSequence` | `EventSequence` | `OrderId` |
|---|---|---|---|
| **Assigned by** | `Sequencer`, on every command *received*, including commands that will be rejected | `state::EventLog`, on every canonical event *emitted* | `MatchingEngine`, on acceptance only |
| **Counter** | `next_command_sequence`, starts at 1, `+1` per command, no gaps | `next_event_sequence`, starts at 1, `+1` per event, strictly monotonic, one counter for the whole exchange run | `next_order_id`, starts at 1, `+1` per accepted order; a rejected `NewOrder` consumes none |
| **Cardinality** | one per command | one or many per command (accept + trades + terminations) | one per accepted order; a cancel-replace allocates a **new** one |
| **Used as** | **FIFO priority key** and the causal reference on every event | the ordering key of the canonical output stream | the identity used by cancel/modify and referenced by trades |
| **Serialized as** | u64 LE in the journal record header and in each event payload as `causing_command_sequence` | u64 LE in `Envelope.sequence` (already documented as monotone within one stream) | u64 LE in each event payload and in every snapshot order record |
| **Restored from** | snapshot header `next_command_sequence` | snapshot header `next_event_sequence` | snapshot header `next_order_id` |

**Priority.** `Priority` is a distinct strong type constructed only via `Priority::from(CommandSequence)`. An order's priority is the `CommandSequence` of the command that established its current queue position: the `NewOrder` that rested it, or the `ModifyOrder` that replaced it. A priority-retaining decrease leaves it untouched. Priority is stored per order and snapshotted, so restore reproduces queue order exactly rather than re-deriving it from insertion order.

**Snapshot header (v1)** carries `{snapshot_version, next_command_sequence, next_event_sequence, next_order_id, last_exchange_time}` plus book state. `restore()` refuses an unknown `snapshot_version`, and additionally refuses a snapshot whose counters are inconsistent with its contents — `next_order_id` at or below any restored `order_id`, or `next_command_sequence` at or below any restored priority. Both refusals ship negative fixtures.

**Acceptance:** a run split as *first half → snapshot → restore into a fresh process → second half* emits byte-identical canonical output to the uninterrupted run, including every `EventSequence` and every `OrderId`. Counter loss is invisible to a round-trip-only test and visible to this one, which is why continuation equality is the acceptance rather than `write == restore→write` alone (both are tested).

### 4.4 Price and quantity representation — **correction 3**

Prices and quantities are integers in the smallest representable unit; the instrument declares the grid on top of them, which is what makes tick and lot validation genuine.

```
PriceUnits    — strong int64, the canonical storage and wire unit for price
QuantityUnits — strong int64, the canonical storage and wire unit for quantity
```

`InstrumentSpec` (in `cpp/exchange/order_book/instrument.hpp`) declares:

```
PriceUnits    price_floor_units;      // grid origin and inclusive lower bound
PriceUnits    price_ceiling_units;    // inclusive upper bound
std::int64_t  tick_size_units;        // > 1 in fixtures, so tick validation is not vacuous
QuantityUnits min_quantity_units;
QuantityUnits max_quantity_units;
std::int64_t  lot_size_units;         // > 1 in fixtures, so lot validation is not vacuous
```

Validation, in a fixed documented order:

- `price_units < floor` or `> ceiling` → `kPriceOutOfBand`
- `(price_units - price_floor_units) % tick_size_units != 0` → `kPriceNotOnTick`
- `quantity_units <= 0` → `kNonPositiveQuantity`
- `quantity_units % lot_size_units != 0` → **`kQuantityNotOnLot`** (new reason, correction 3)
- `quantity_units < min` or `> max` → `kQuantityOutOfRange`

Consistency argument, stated in ADR-0010 and tested: every accepted quantity is a multiple of `lot_size_units`, a fill is `min(remaining_maker, remaining_taker)`, and the minimum of two multiples of L is a multiple of L — so every fill, every residual and every level aggregate is a lot multiple. A property test asserts it after every generated operation. Every resting price is on the tick grid by construction, so the level index is keyed on price units that are always on-grid, and the price domain has a finite, documented cardinality `(ceiling - floor)/tick + 1` — the price-domain assumption AEGIS-038 requires.

M1 attaches **no** currency, multiplier, exponent or display scale to a price unit; that is AEGIS-011 (M2) instrument metadata. M1 computes no notional, so no `price × quantity` product exists to overflow. Quantity accumulation into level aggregates is checked against `int64` overflow at the accumulation site and covered by UBSan.

### 4.7 Benchmarks and allocation tracking — **correction 5**

**Allocation tracking is per-instance, not process-global.** No `operator new` override anywhere. `OrderBook`, its slab, its order index and its level index are `std::pmr` containers constructed with an injected `std::pmr::memory_resource*` (defaulting to `std::pmr::get_default_resource()`). `tests/cpp/support/counting_resource.hpp` is a `memory_resource` that counts `do_allocate`/`do_deallocate` calls and bytes for the one book that owns it. This is deterministic, has no global mutable state (which the architecture checker bans in these layers anyway), needs no test ordering discipline, and behaves identically under `asan-ubsan` — so the earlier "exclude the allocation test under sanitizers" caveat is gone.

AEGIS-037's acceptance becomes: after construction and warmup within reserved capacity, a steady-state add/cancel/match cycle performs **zero** allocations on the injected resource.

**`aegis_exchange_bench` ships three named, seeded, repeatable workloads**, each with warmup, a fixed operation count, and repeated runs:

1. **`lookup_cancel`** (AEGIS-036) — build N resting orders across M levels, then K seeded lookups and cancels by `OrderId`.
2. **`single_fill_aggressor`** (AEGIS-039) — every aggressor consumes exactly one resting order.
3. **`multi_fill_multi_level_aggressor`** (AEGIS-039) — every aggressor sweeps k resting orders across j levels, with sub-cases k ∈ {2, 4, 8, 16, 32}.

A fourth run reproduces the `docs/BENCHMARK_POLICY.md` mix (45 add / 30 cancel / 10 modify / 10 marketable / 5 multi-level) so the policy's required workload is present.

Each run writes JSON to `experiments/evidence/AEGIS-036/` or `experiments/evidence/AEGIS-039/` carrying the full policy disclosure — CPU model, RAM, OS/kernel, **virtualization: WSL2**, compiler and version, optimization flags, build type, sanitizer and assertion state, governor/affinity (recorded as unknown where the host cannot report it), warmup procedure, message mix, event count, instruments/levels/orders/fill distribution, allocation count, median/p95/p99/p99.9/max, throughput, raw artifact path and the reproducible command.

**Claim boundary, stated in the artifact and in `docs/LIMITATIONS.md`:** timings are `local_non_comparable: true`. The *asserted* acceptance is operation counts, which are deterministic; timing is recorded because the policy requires it to be recorded, and no latency, throughput, low-latency, HFT or CV claim is derived from any M1 number. Tail-latency measurement and claims belong to M8 (AEGIS-052/053).

### 4.8 Client order IDs and terminal orders — **correction 7**

**Scope.** Duplicate detection is over the pair `(participant_id, client_order_id)`. Two participants may use the same client order id; one participant may not.

**Retention.** Uniqueness is enforced over **live orders only**. The book holds a `(ParticipantId, ClientOrderId) → OrderId` map containing exactly the currently open orders; the entry is erased when the order terminates. Reuse of a client order id after its order has terminated is **accepted**, and this is documented in ADR-0011 and `docs/LIMITATIONS.md`. The map is derivable from the restored book, so restore rebuilds it rather than persisting it.

**`kOrderAlreadyTerminal` is removed from the reject enum.** Retaining it would require an unbounded tombstone set that must be snapshotted and governed by a retention policy that no requirement specifies and that M1 must not invent. Cancel or modify of an unknown, already-filled, already-cancelled or already-replaced `OrderId` therefore returns **`kUnknownOrderId`** consistently — one reason, one testable row, no unbounded state. An order still live but owned by a different participant returns `kNotOrderOwner` (ownership is checkable because the order is live).

**Reject enum after corrections 3 and 7** — this enum *is* the AEGIS-035 validation matrix:
`kUnknownInstrument`, `kDuplicateClientOrderId`, `kNonPositiveQuantity`, `kQuantityNotOnLot`, `kQuantityOutOfRange`, `kPriceNotOnTick`, `kPriceOutOfBand`, `kPriceOnMarketOrder`, `kUnknownOrderId`, `kNotOrderOwner`, `kModifyBelowFilled`, `kMalformedMessage`.

Every enumerator is a *validation* failure decided before an order exists. Outcomes that depend on the state of the book — an unfilled market residual, an empty book — are not rejections and have no reason code (§3); they are terminations of an accepted order. This keeps the AEGIS-035 matrix a closed set in which every row is reachable from a malformed or invalid command alone.

### 4.9 Invariant scope — **correction 8**

`check_invariants(const OrderBook&, InvariantScope)` has two scopes, and the difference is documented in ADR-0010 and in the header:

- **`InvariantScope::kStructural`** — holds at every point at which the book is observable, including mid-match: order-index ↔ queue bijection; free list disjoint from the live set; every level's `aggregate_quantity` equals the sum of `remaining` over its queue; `0 < remaining ≤ original_quantity`; priorities strictly increasing along each queue; bids descending and asks ascending in the level index.
- **`InvariantScope::kQuiescent`** — the structural set **plus** the invariants that are only meaningful once a command has been fully applied: **the book is uncrossed (`best_bid < best_ask`)**, no emptied level is retained in the index, and per-order conservation (§4.10 P1) holds for every live order.

**The uncrossed-book invariant is checked only at command boundaries** — after `MatchingEngine::apply()` returns — and never during the matching loop or after a raw book mutation made by a test helper. An aggressor is legitimately crossed with the book for the duration of matching; asserting otherwise mid-loop would either be false or force the engine into a shape that hides the transition. Debug-build assertions inside matching use `kStructural` only. The fuzz harness calls `kQuiescent` after every generated **command**, and `kStructural` after every internal step it can observe.

### 4.10 Conservation properties — **correction 4**

The old "submitted = filled + resting + cancelled" is dropped: it silently double-counts, because a single trade increments the filled quantity of both the maker and the taker.

**P1 — per-order conservation.** For every *accepted* order `o`, at every quiescent point:

```
original_quantity(o) = cumulative_filled(o) + remaining(o) + cancelled_quantity(o)
```

`cancelled_quantity` accumulates: quantity removed by a `CancelOrder`; the unfilled residual of an accepted market order, terminated as `kResidualCanceled`; the decrement of a priority-retaining quantity decrease; and, when an order is terminated by cancel-replace, its whole remaining quantity. A replacement is a distinct `OrderId` with its own `original_quantity`, so the equation is well formed on both sides of a replace. Rejected commands create no order and contribute nothing. `remaining(o) = 0` for every terminated order.

**P2 — aggregate conservation, counting both sides.** Over a whole run:

```
Σ_{o ∈ buy orders}  cumulative_filled(o) == Σ_{t ∈ trades} quantity(t)
Σ_{o ∈ sell orders} cumulative_filled(o) == Σ_{t ∈ trades} quantity(t)
Σ_{all orders}      cumulative_filled(o) == 2 × Σ_{t ∈ trades} quantity(t)
```

Each execution pairs exactly one maker with exactly one taker and adds the same quantity to both, which is precisely why the total is twice the traded quantity. Per side it is once.

**P3 — book aggregate.** `Σ_{levels} aggregate_quantity == Σ_{live resting orders} remaining(o)`, and per level `aggregate_quantity == Σ_{o in queue} remaining(o)`.

**P4 — lot alignment.** Every `remaining`, every `cumulative_filled`, every `cancelled_quantity` and every level aggregate is a multiple of `lot_size_units` (§4.4).

P1, P3 and P4 are checked by the invariant checker after every command; P1–P4 are all asserted by `tests/cpp/property/test_quantity_conservation.cpp` over generated operation sequences, with the ledger accumulated from the emitted event stream rather than from book internals — so a bug that corrupts both the book and its own accounting is still caught.

### 4.11 Fixtures and determinism wiring

## 6. Dependency and clock model

```
command fixture / caller
        │  EventTime from source
        ▼
Sequencer ── CommandSequence + ExchangeTime ──► MatchingEngine (single writer per book)
                                                     │  allocates OrderId on acceptance
                                        OrderBook ◄──┤  via MatchingPolicy
                                                     ▼
                                     state::EventLog ── allocates EventSequence ──► canonical envelopes
                                                     │
                                     state::Snapshot (book + all three counters + exchange time)
```

Layer edges used: `sequencer → {common, events}`; `order_book → {common, events}`; `matching → {common, events, order_book}`; `state → {common, events, sequencer, order_book}`; `app → all of the above`. No edge points to `participant`, `replay`, `memory`, `queues`, `market_data` or Python. `cpp-bindings` keeps `may_depend_on: [cpp-common, cpp-events]`, so Python reaches the engine through the replay CLI, not pybind11 — engine bindings are AEGIS-229 (M2).

Clocks: commands carry `EventTime`; the sequencer derives `ExchangeTime = max(previous, event_time)`, stamping a regressing input forward and counting it rather than rejecting it silently. `MonotonicTime` appears only in `bench_main.cpp` and is never serialized. `ReceiveTime`, `DecisionTime`, `SubmitTime`, `AckTime` are participant domains and appear nowhere in M1. FIFO priority is `CommandSequence`, so book behavior is independent of every clock.

## 8. Failure modes anticipated

1. **Timestamp-tie priority** — two orders sharing a nanosecond ordered by comparator luck. Mitigated by `CommandSequence` as the priority key and an explicit tie test.
2. **Identifier conflation** — reusing one counter for priority, event ordering and order identity, so a snapshot that loses one silently reproduces plausible output. Mitigated by three non-convertible strong types, three snapshotted counters, and continuation equality as the acceptance.
3. **Hash-order leakage** — iterating the order index into output or snapshot bytes. Mitigated: canonical serialization order is (price units, priority); the harness varies `PYTHONHASHSEED`; the lint test forbids clock reads.
4. **Dangling handles on slab growth.** Mitigated by index handles and the bijection invariant.
5. **Empty-level retention** corrupting best bid/ask. Explicit quiescent invariant plus AEGIS-034 tests.
6. **Uncrossed-book assertion fired mid-match**, forcing a contorted engine shape. Mitigated by the two invariant scopes (§4.9).
7. **Vacuous tick/lot validation** if price were stored in ticks and quantity in lots. Mitigated by units-plus-grid representation with fixtures where `tick_size_units > 1` and `lot_size_units > 1`.
8. **Unbounded tombstone state** for terminal-order rejects. Removed by design (§4.8).
9. **Global allocation counters** colliding with sanitizers or with test ordering. Removed by per-instance `memory_resource` injection.
10. **Scope-guard failure from unmerged M0** (measured: 25 paths) blocking every CI run of M1.
11. **Architecture check flapping** on the BUILD_STATE flip. Mitigated by the slice-1 shape.
12. **Over-reach into M8** — a free list becoming an arena, an allocation counter becoming a latency claim. Boundary stated in ADR-0010; no number enters `.md` prose without an `evidence:` marker.
13. **`--check-deferred M1` failing at closure** on obligations only the owner can discharge (§11).
14. **Empty ctest layer** if new tests land under an unknown label. Mitigated by reusing `unit` / `property`.
15. **`filterwarnings = ["error"]` and strict mypy** breaking new Python modules. Run `ruff` and `mypy` per slice, not at the end.

## 9. ADRs required

- **ADR-0009 — Exchange domain model and wire vocabulary.** Integer price and quantity units, strong ID types, permanent `MessageType` numbering in the 1..999 band, why domain messages live in `cpp/events`, the symmetric Python peer.
- **ADR-0010 — Book structure, complexity claims and invariant scope.** Pre-sized order index, `MapLevelIndex` behind an interface, index-handle slab with intrusive FIFO, injected `memory_resource` instead of global `operator new`, tick/lot grid and price-domain assumptions, the two invariant scopes and why the uncrossed-book check is quiescent-only, permitted complexity wording, and the exact boundary against AEGIS-042/043.
- **ADR-0011 — Order lifecycle semantics.** In-place decrease vs cancel-replace with a new `OrderId`; market-order acceptance and residual termination, including the empty book, and why liquidity is not a reject reason; the reject taxonomy as a closed set of validation failures, including `kQuantityNotOnLot`; `(participant_id, client_order_id)` scope, live-only uniqueness, client-id reuse after termination, and the removal of `kOrderAlreadyTerminal` in favour of `kUnknownOrderId`; the deliberate absence of STP, TIF and auctions.
- **ADR-0012 — Exchange sequencing, layering and determinism.** The three identifier spaces and their allocation, serialization and restore rules; derived `ExchangeTime`; the `cpp-exchange-state` and `cpp-exchange-app` layers and why the DAG needed them; **the re-dating of `cpp-exchange-market-data` from M1 to M3** with the AEGIS-064–070 and `milestone_scope.yaml` reasoning; the canonical event-log form; how AEGIS-005's obligation is discharged.
