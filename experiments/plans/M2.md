# AEGIS M2 — Futures Lifecycle + Replay: Plan of Record (rev. 4)

> **Rev 2** replaced the circular in-branch SSH anchor with a protected-`main` root of trust.
> **Rev 3** added an external credential boundary: the credential in Claude's environment could
> merge to `main` and rewrite the ruleset, so "only the owner can merge" was an assumption, not a
> control.
> **Rev 4** corrects two errors in rev 3's credential design — the machine-account +
> fine-grained-PAT combination is not viable on a personal-account repository, and the claim
> "Claude cannot merge" was false. The agent now authenticates as a private **GitHub App**, and
> the invariant is restated as **"no commit enters `main` without a fresh approving review from
> the separate owner identity."**
> The M2 requirement scope, futures and replay architecture, slices, residual decisions, evidence
> strategy and verification cadence are **unchanged since rev 2**.

## 0. MEASURED STARTING STATE OF THE CREDENTIAL BOUNDARY

Read-only inspection of the live environment, `2026-08-09`:

```
gh auth status      → account integrals234, scopes: gist, read:org, repo, workflow
gh api user         → login integrals234  (= the repository owner)
gh api repos/integrals234/aegis .permissions
                    → {"admin": true, "maintain": true, "push": true, "triage": true, "pull": true}
gh api repos/.../collaborators/integrals234/permission
                    → {"permission": "admin", "role_name": "admin"}
git remote -v       → https transport, credential = the same token
ruleset 20596537    → pull_request{required_approving_review_count: 0,
                                   require_last_push_approval: false},
                      required_status_checks{strict: true, 10 contexts},
                      bypass_actors: []
```

**Consequence.** The credential available to Claude today can:

1. **Merge any PR into `main`** — `repo` scope, admin, and `required_approving_review_count: 0`
   means a PR with green checks is mergeable by whoever holds the token.
2. **Rewrite or delete the "Protect main" ruleset** — `PUT`/`DELETE /repos/{r}/rulesets/20596537`
   requires repository admin, which this token has.
3. **Therefore push directly to `main`** — by doing (2) first.

`bypass_actors: []` provides no protection against an actor who can rewrite the ruleset.
So under rev 2, an agent could author a `policy.yaml` PR (which the governance gate correctly
passes, because a candidate policy is inert), then merge it with this credential, placing
attacker-controlled policy on the very `main` that is the root of trust.

**Rev 2's root of trust was sound. Its assumption about who can write to that root was not.**

## 1. REVISED R8 THREAT MODEL

### 1.1 The in-repository vulnerability (unchanged from rev 2)

`tools/check_scope.py:29` and `tools/check_frozen.py:32` both parse owner approvals from the
same `- Owner-approved scope changes:` line of `docs/BUILD_STATE.md`, which
`configs/milestone_scope.yaml` lists under `always_allowed`. Four self-authorization routes:

1. **Scope** — append a path to the approval line; `check_scope` skips it (`check_scope.py:99`).
2. **Frozen files** — `check_frozen.check_history` reads the *same* line (`check_frozen.py:113`)
   and its `protected` set is `manifest ∪ {frozen_hashes.json}`. Name both `docs/MASTER_SPEC.md`
   and `requirements/frozen_hashes.json`, edit the spec, recompute the digest → content **and**
   history checks pass. The `PreToolUse` hook does not close this; shell writes bypass it.
3. **Scope policy** — `configs/milestone_scope.yaml` is in `configs/**`, allowed every milestone.
4. **Active milestone** — `- Active milestone: M9` has an empty `denied` list and a tree-wide
   `allowed` list.

### 1.2 Why the rev-1 in-branch signature design was circular

Rev 1 verified `anchor.yaml.sig` against `configs/governance/allowed_signers` and defended the
signer file by pinning its digest *inside the signed anchor*. Both live in the candidate branch:

```
1. ssh-keygen -t ed25519 -f attacker_key
2. attacker_key.pub → configs/governance/allowed_signers
3. rewrite anchor.yaml: new signer digest + arbitrary approvals + arbitrary milestone
4. ssh-keygen -Y sign -f attacker_key -n aegis-governance anchor.yaml
5. verification succeeds — signature, signer file and payload are mutually consistent
```

No mismatch, because the attacker updates the digest *and* re-signs. A hash chain whose every
link is inside the attacker's writable set proves internal consistency, not authenticity. The
same defect applies to any verifier supplied by the branch under judgement.

### 1.3 Why the rev-2 model was still incomplete

Rev 2 correctly moved the root of trust to protected `main`, then asserted "the agent cannot
merge to `main`; only the owner can." §0 shows that was false. The full attack:

```
1. edit configs/governance/policy.yaml on a feature branch
     (active_milestone: M9, or an approval for any path)
2. open a PR
3. authoritative governance gate PASSES — correctly: a candidate policy is inert,
   and policy.yaml is a deliberately always-permitted path
4. the ten correctness checks pass — nothing malicious is in the code
5. merge the PR with the environment credential  ← the actual breach
6. main now carries attacker-controlled policy; every subsequent PR is judged by it
```

Step 5 is the whole exploit. Step 2 of §0 is the shortcut version: rewrite the ruleset and push.

### 1.4 Corrected attack model

**Assume the agent has full write access to every file in the candidate branch — all tooling,
all policy, all workflow files, all tests — and can run arbitrary local shell commands, and
holds whatever GitHub credential is present in its environment.**

The security model may therefore rely on exactly one thing: **that the credential in Claude's
environment is technically incapable of the authoritative actions.** It may not rely on a
prompt instruction saying Claude must not merge. A prompt is a policy; the token is the control.

## 2. REVISED GOVERNANCE TRUST ARCHITECTURE

### 2.1 Two boundaries, not one

```
   ┌─ BOUNDARY 1: CREDENTIAL (external, enforced by GitHub) ──────────────────┐
   │                                                                          │
   │  OWNER CREDENTIAL  (integrals234, admin)  — never in Claude's environment │
   │    • merge PRs into main                                                 │
   │    • create/modify/delete rulesets                                       │
   │    • change repository Actions settings                                  │
   │    • approve pull requests                                               │
   │                                                                          │
   │  AGENT CREDENTIAL  (GitHub App installation token) — Claude's env        │
   │    • push feature branches      • open PRs                               │
   │    • read PRs / checks / logs / artifacts / rulesets                     │
   │    ✗ ruleset write  ✗ admin endpoints  ✗ approve any PR                  │
   │    ⚠ CAN call merge — but only after a fresh owner approval (§2.3)       │
   └──────────────────────────────────────────────────────────────────────────┘
                                     │
   ┌─ BOUNDARY 2: CONTENT (in-repo, enforced by the gate) ────────────────────┐
   │  PROTECTED MAIN                                                          │
   │   ├── configs/governance/policy.yaml      ← sole authority               │
   │   ├── configs/milestone_scope.yaml        ← trusted scope policy         │
   │   ├── requirements/frozen_hashes.json     ← trusted frozen digests       │
   │   ├── tools/governance/authoritative_check.py  ← trusted verifier        │
   │   └── .github/workflows/governance.yml    ← trusted job definition       │
   │                    │ pull_request_target: base context                   │
   │                    │ candidate read ONLY as data (GitHub API)            │
   │                    ▼                                                     │
   │   "Authoritative governance gate (R8)" → required status check           │
   └──────────────────────────────────────────────────────────────────────────┘
```

Boundary 2 is unchanged from rev 2 and remains correct. Boundary 1 is what rev 3 adds, and
without it Boundary 2's root is writable by the thing it constrains.

### 2.2 The agent credential — a GitHub App installation

**Corrected 2026-08-09.** The rev-3 proposal — a machine account added as a repository
collaborator, authenticating with a fine-grained PAT — **is not viable**. GitHub's documented
fine-grained-PAT limitations state that such a token cannot be used to contribute to a repository
its owner is an *outside collaborator* on, and a collaborator on a personal-account repository is
exactly that case. `integrals234/aegis` is a personal-account repository, so the combination
would fail on the first `git push`.

**Replacement: a private GitHub App owned by `integrals234`, installed only on
`integrals234/aegis`, authenticating with installation access tokens.**

| App setting | Value |
|---|---|
| Owner | `integrals234` (personal account) |
| Visibility | **Private** — "Only on this account" |
| Installed on | `integrals234/aegis` **only** |
| Webhook | Disabled — nothing subscribes to events |
| User authorization / OAuth | Not enabled |

Repository permissions — the complete grant, nothing beyond the workflow's need:

| Permission | Level | Why |
|---|---|---|
| Contents | **Write** | push feature branches (unavoidable; see §2.3) |
| Pull requests | **Write** | open, update, comment on PRs |
| Workflows | **Write** | G0 adds `governance.yml`; Slice 1 retargets `ci.yml` |
| Actions | **Read** | run status, logs, artifact download |
| Metadata | **Read** | mandatory baseline |
| Administration | **Read** | ruleset inspection (V5, O6 confirmation) — read only |
| Administration | **— NOT GRANTED —** | **ruleset write is the capability being denied** |
| Everything else | **— NOT GRANTED —** | no Secrets, Environments, Webhooks, Pages, Packages, Deployments, Members, Security |

*Administration: Read is the one judgement call.* `GET /repos/{r}/rulesets` requires it, and the
plan uses ruleset inspection at V5 and to confirm O6 landed. It is strictly read-only. If the
owner prefers to withhold it, V5 is lost (ruleset state must then be reported by the owner);
V6's denial proof still holds, and nothing else in the plan changes.

**Identity.** An installation token acts as `aegis-agent[bot]`, a distinct actor from
`integrals234`. That separation is what makes required approving reviews workable: the bot
authors every agent PR, GitHub refuses self-approval, and the owner — a different identity — can
approve. A single shared identity deadlocks here, which is why two identities are structural.

**Token handling.** Installation access tokens expire after one hour. The App's private key lives
**outside the repository** at `~/.config/aegis/aegis-agent.pem` (mode `0600`), and a small
owner-installed helper mints a fresh token on demand (build an RS256 JWT with `openssl`, exchange
it at `POST /app/installations/{id}/access_tokens`). `GH_TOKEN` and the git credential helper both
draw from it. G0 commits a documented, reviewed copy of the helper at
`tools/governance/mint_installation_token.sh` plus `docs/ENVIRONMENT.md` instructions for
reproducibility — but the **operative** helper and the key live outside the repository.

**Owner-confirmed 2026-08-09: `Workflows: Write` is granted**, so the agent authors G0's
`governance.yml` and Slice 1's `ci.yml` retarget itself. This makes the §2.4 Actions hardening
**load-bearing rather than defence-in-depth**, and O4 is therefore a hard prerequisite of G0, not
a nice-to-have. The alternative — withholding it and making both edits owner-authored PRs — was
rejected as too costly across M2–M9. This decision is closed; do not reopen it.

### 2.3 The merge capability — corrected invariant

**`Contents: Write` permits calling the merge endpoint.** `PUT /repos/{r}/pulls/{n}/merge`
requires `Contents: Write` + `Pull requests: Read`; pushing branches requires the same `Contents:
Write`. The two **cannot be separated by permission**. So the earlier claim — *"Claude cannot
merge any PR"* — was wrong and is withdrawn.

> **The actual security invariant:**
> **Claude cannot cause any commit to enter `main` without a fresh approving review from the
> separate owner identity.**

That invariant is enforced at the ruleset layer, not the token layer:

| Ruleset setting | From | To | Effect |
|---|---|---|---|
| `required_approving_review_count` | 0 | **1** | an approval the bot cannot supply is mandatory |
| `require_last_push_approval` | false | **true** | the approval must post-date the last push |
| `dismiss_stale_reviews_on_push` | false | **true** | any new bot commit voids a prior approval |
| `bypass_actors` | `[]` | `[]` | unchanged — nobody bypasses, including Apps |
| required checks | 10 | **11** | adds `Authoritative governance gate (R8)` (step O6) |

GitHub refuses `POST /pulls/{n}/reviews {"event":"APPROVE"}` from the PR's own author with **422
"Can not approve your own pull request."** `aegis-agent[bot]` authors every agent PR and holds no
second identity, so it can never satisfy the requirement. And because a post-approval push both
dismisses the review and fails `require_last_push_approval`, the bot cannot approve-then-push, nor
push-then-reuse a stale approval.

**What this leaves.** After the owner approves an exact diff, the bot could mechanically call
merge on that same diff. That is not an escalation: the owner has already approved precisely those
bytes, and any change to them voids the approval. **The authoritative human action is the owner's
approval of the exact final diff, not the button press.**

**Project workflow rule (not a security boundary).** Claude nonetheless stops before merging and
leaves the merge to the owner, for every PR in this plan. This is a convention that keeps the
human in the loop at a second point; it is documented as a convention and is *not* counted as a
control anywhere in §5.

### 2.4 Repository Actions settings — closing the `GITHUB_TOKEN` escalation

`Workflows: Write` lets the agent add a workflow file on a branch. A hostile workflow could try
to use `GITHUB_TOKEN` to approve or merge its own PR. Two repository settings, owner-set, close
this and are **mandatory, not optional**:

- **Settings → Actions → General → Workflow permissions → "Read repository contents and
  packages permissions"** (default `GITHUB_TOKEN` becomes read-only).
- **Uncheck "Allow GitHub Actions to create and approve pull requests."**

Defence in depth: `.github/workflows/**` is in `governance_paths`, so any workflow change needs
an owner-merged approval before it can land on `main` anyway; and `pull_request_target` reads its
definition from base, so a head-side workflow edit never runs privileged.

### 2.5 The trusted policy file — `configs/governance/policy.yaml` (unchanged from rev 2)

```yaml
policy_version: 1
active_milestone: M1              # bootstrap value; M2 activation is a separate owner-merged PR

governance_paths:                 # changing any of these requires an approval below
  - configs/milestone_scope.yaml
  - requirements/frozen_hashes.json
  - .github/workflows/governance.yml
  - .github/workflows/ci.yml
  - tools/governance/**
  - tools/check_scope.py
  - tools/check_frozen.py
  - .claude/settings.json
  - .claude/hooks/protect_spec.py

# configs/governance/policy.yaml itself is deliberately ALWAYS permitted in a PR:
# it is inert until merged, and merging now requires the owner credential (§2.2-2.3).

approvals: []                     # exact paths only — never globs
```

An approval entry is `{id, milestone, paths[], reason, granted_on, granted_by_pr}` with exact
paths. An approval whose `milestone` ≠ `active_milestone` is inert, so permissions expire with
the milestone automatically.

### 2.6 The authoritative verifier and workflow (unchanged from rev 2)

`tools/governance/authoritative_check.py` runs from the **base** checkout under
`pull_request_target`. Six fail-closed checks: (1) scope from main's `milestone_scope.yaml` and
`policy.active_milestone`; (2) governance-path changes need an exact-path approval; (3) frozen
paths still hash to **main's** digests at the candidate head SHA; (4) frozen-path changes need an
approval; (5) candidate `BUILD_STATE.md` active milestone equals main's policy; (6) policy present,
parseable, known `policy_version`, file list obtainable — otherwise fail.

The privileged job **never places the candidate tree on disk and never executes it**. Candidate
reads go through `gh api repos/{r}/pulls/{n}/files` and
`gh api repos/{r}/contents/{path}?ref={head_sha}`. It does not check out head, source candidate
scripts, run candidate Python or binaries, or install candidate-controlled dependencies — the
lockfile it installs is main's. A `CandidateReader` abstraction gives `GitHubApiReader` for CI and
`GitShowReader` for local preflight and tests.

### 2.7 Local checks vs. the authoritative check (unchanged from rev 2)

`tools/check_scope.py` and `tools/check_frozen.py` remain, retitled **ADVISORY** in docstring and
success output, and stay in `ci_local.sh`. New `scripts/governance_preflight.sh` fetches
`origin/main` into a throwaway `git worktree` and runs **main's** verifier against the local diff —
the same verdict as CI, before a PR exists. It is local convenience; tampering with it changes no
PR verdict.

### 2.8 Owner approval model

A genuine exception is granted by the owner merging a PR that adds one `approvals` entry. Under
rev 3 that ceremony now has two locks:

1. **Content lock** — the entry has no effect until it is on `main`.
2. **Credential lock** — reaching `main` requires an approving review plus a merge, both of which
   need the owner credential that is absent from Claude's environment.

Properties: **explicit** (named entry with a reason), **narrow** (exact paths, no globs),
**milestone-scoped** (auto-expires), **auditable** (git history on `main`, with the granting PR
number), **non-self-service** (technically, not by instruction), **deterministic** (a file
comparison), **low friction** (one small PR per milestone).

Rejected alternatives: in-branch signed approvals (circular, §1.2); signed commits (key management,
rebase-fragile); GitHub labels (mutable by any write-capable token, including the agent's);
relying on `required_approving_review_count` with a single identity (deadlocks on GitHub's
self-approval ban — this is *why* §2.2 needs a separate App identity).

### 2.9 Honest residual limits

1. **The G0 bootstrap PR is trusted by owner review alone.** Irreducible — it is the trust root.
   Mitigated by keeping it mechanism-only and small.
2. **`Workflows: Write` is the widest permission the agent holds** (owner-confirmed, §2.2). Its
   only mitigations are §2.4's Actions hardening and the governance-path approval requirement, so
   **O4 is load-bearing**: if `GITHUB_TOKEN` is ever returned to write-by-default, or "Actions
   create and approve pull requests" is re-enabled, attack N reopens. O4's settings are therefore
   re-verified alongside the credential battery at G0 merge and at M2 closure.
3. The gate governs **scope, frozen-file and milestone authority**. It does not prove tests were
   not gutted; that remains owner review plus the eleven checks.
4. Depends on documented GitHub semantics: `pull_request_target` uses the base-branch workflow
   definition and base-ref checkout; self-approval is refused with 422; ruleset writes require
   repository admin.
5. **The credential boundary is only as good as the environment.** If an owner-credentialed
   `gh`/git configuration is ever restored to this machine, Boundary 1 is gone. §3 step V is a
   recurring check, not a one-time one.
6. **The App private key is readable by the agent.** It sits on the same machine, so possession is
   not a barrier. This is acceptable because possessing the key grants **exactly** the
   installation's permission set and nothing more — the boundary is the App's permissions, not
   key secrecy from the agent. The existing `.claude/settings.json` deny rules
   (`Read(**/*.pem)`, `Bash(cat *.pem)`) reduce casual exposure but are not the control. The key
   is kept outside the repository so it can never be committed, and rotating it is an owner
   action that invalidates every prior installation token.
7. **After an owner approval, the merge itself is mechanical** (§2.3). The control is approval of
   the exact diff, not who presses merge. Claude's stop-before-merge rule is a workflow
   convention and is deliberately excluded from the §5 proof.

## 4. GITHUB CLI EXECUTION MODEL AND CREDENTIAL VERIFICATION

### 4.1 What Claude may do — and what it is technically prevented from doing

| Claude does (installation token) | Claude **cannot** (no permission) | Claude **can technically**, but is bounded |
|---|---|---|
| push feature branches (`Contents: Write`) | approve any pull request | **call the merge endpoint** — only after a fresh owner approval of the exact diff (§2.3) |
| `gh pr create`, update, comment | create, update or delete a ruleset | |
| `gh pr view/list/diff`, `gh api pulls/{n}/files` | change Actions or security settings | |
| `gh run list/view/watch`, download artifacts | push directly to `main` | |
| `gh api .../rulesets` — **read only** | add or remove collaborators | |
| `gh api .../check-runs`, commit statuses | manage secrets, environments, webhooks | |
| delete its own merged feature branches | install or modify the App itself | |

Two corrections to earlier revisions:

1. This **supersedes** rev 1/rev 2's line about Claude "updating repository rules through the API
   where owner-authorized." Ruleset writes are not delegated — they are unavailable.
2. The middle column no longer claims Claude cannot merge. It can call the endpoint; what it
   cannot do is make a PR *mergeable* without an owner approval (§2.3). By project convention
   Claude still stops and leaves the merge to the owner, but that is a convention, not a control.

### 4.2 Non-destructive credential capability verification (bootstrap step V)

Every probe's *expected* result is a rejection, so nothing is merged, changed or weakened. Where
a write endpoint is called, the payload is chosen so that even a permitted call cannot alter state.

**Two absolute rules.** (1) A write endpoint is probed **only** with a structurally invalid
payload, so authorization-denied (403) and validation-rejected (422) are the only possible
outcomes and neither can change state. (2) The **merge endpoint is never called at any point** —
under the corrected invariant (§2.3) a post-approval merge would *succeed*, so it is not a safe
probe and its absence from this battery is deliberate.

### Boundary 1 — credential authority (new in rev 3)

**Invariant under proof:** *no commit enters `main` without a fresh approving review from the
separate owner identity.* Not "Claude cannot merge" — see §2.3.

| | Attack | Verdict | Mechanism |
|---|---|---|---|
| **K** | Author a `policy.yaml` PR — which the gate correctly passes — then get it into `main` to install attacker-controlled policy | **FAIL** | The PR is `mergeable_state: blocked` with zero reviews (V9). `required_approving_review_count: 1`, and the bot authors the PR so GitHub refuses its approval with 422 (V10). approving review from an identity the agent does not hold.** Boundary 2 makes candidate content
non-authoritative; Boundary 1 makes the root of trust unreachable without the owner.

## 6. REVISED ADR-0014 PLAN

**ADR-0014 — Governance trust boundary (R8)**

- **Problem.** Every in-repository authority surface for scope, frozen files and the active
  milestone is agent-writable (four routes, §1.1). Any fix rooted inside the candidate branch is
  circular (§1.2). And a fix rooted in protected `main` is only as strong as the credential set
  that can write to `main` — which in the measured starting state included the agent's own
  environment (§0, §1.3).
- **Decision.** Two boundaries. **Content:** `configs/governance/policy.yaml` on protected `main`
  is the sole authority; a `pull_request_target` job runs **main's** verifier against the candidate
  diff, reading the candidate only as data; in-branch checkers are advisory. **Credential:** the
  environment authenticates as a private **GitHub App** installed only on this repository, using
  short-lived installation tokens, granted no `Administration: Write`; and the ruleset requires an
  approving review that the App's identity cannot produce for its own PRs. The invariant is
  **"no commit enters `main` without a fresh approving review from the separate owner identity"** —
  *not* "the agent cannot merge", which is false because merge and push share `Contents: Write`.
- **Alternatives rejected.** In-branch signed anchor (circular, §1.2). Signed commits (key
  management; rebase-fragile). `pull_request` workflow fetching main's checker (the workflow *file*
  still comes from head, so the job can be neutered while keeping its name). GitHub labels (mutable
  by any write-capable token). Single identity with required reviews (deadlocks on GitHub's
  self-approval ban). **Machine account + fine-grained PAT (rev 3's proposal) — not viable: a
  fine-grained PAT cannot contribute to a repository its owner is an outside collaborator on, which
  is exactly a collaborator on a personal-account repository.** Separating merge from push by
  permission (impossible — both require `Contents: Write`; hence the ruleset-layer fix, §2.3).
  Prompt-level "Claude must not merge" (a policy, not a control — retained as a workflow
  convention but explicitly excluded from the proof).
- **Compatibility with M1.** No M1 behaviour changes. `check_scope.py` / `check_frozen.py` keep
  their interfaces and stay in `ci_local.sh`. The historical BUILD_STATE record of M1's approvals
  is preserved verbatim, retitled. No milestone report, evidence file or `implementation_status.json`
  entry is rewritten. No frozen file is modified.
- **M3+ implications.** One small owner-merged policy PR per milestone transition and per genuine
  exception; approvals expire automatically. The credential boundary is set up once and re-verified
  at each milestone close. The pattern extends unchanged through M9.
- **Consequences and limits.** §2.9 recorded verbatim, including: the G0 bootstrap PR is trusted by
  owner review alone; `Workflows: Write` is the widest agent permission and depends on the Actions
  hardening; the gate does not prove test integrity; the design depends on documented GitHub
  semantics; and the credential boundary is environment-dependent and therefore **verified
  repeatedly, not assumed**.

## 7. CORRECTED CANONICAL REPLAY ORDER *(rev 2, unchanged)*

Rev-1's "no tie-break rule is needed" was wrong. `record_index` **is** the deterministic final
tie-breaker and is what makes the key total.

**Canonical order:** `(event_time_ns, source_sequence, contract_symbol, record_index)`.

**`record_index`** — zero-based ordinal of a normalized record within the canonical ingestion
result. Assigned in one deterministic pass: input paths made repository-relative with POSIX
separators, deduplicated and **sorted lexicographically** → `source_file_id`; `line_number` is the
1-based physical line (or 0-based array element index); normalization and the malformed/duplicate
rejection policies run; `record_index` is then assigned over the **surviving** records in
`(source_file_id, line_number)` order, contiguously from 0, with rejected records logged separately
by `(source_file_id, line_number)` so nothing is lost and no gaps arise.

**Persisted** as an explicit field of the canonical input artifact and covered by the manifest's
input digest; replay reads it and **never recomputes it**. A pure function of (input bytes, input
path set, ingestion config) — independent of memory layout, dict/set iteration order,
`PYTHONHASHSEED`, threading, scheduling, wall clock and build configuration. Identical across
repeated ingestion, separate processes, debug and release, snapshot/resume, and all four pacing
modes. Two records can never share all four key components. The replay cursor stores the last
emitted `record_index`; resume continues strictly above it.

**Tests:** identical assignment across processes with differing `PYTHONHASHSEED`; **input paths
supplied in shuffled argument order produce identical indices** (proves the internal sort, not the
caller, determines order); a genuine four-way tie replays in `record_index` order byte-identically
in all four pacing modes; mid-stream cursor resume reproduces the tail of an uninterrupted run
exactly; changing the rejection policy changes indices *and* the manifest digest together, never one
without the other. ADR-0018 records these as decisions.
