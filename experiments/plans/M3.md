**Do AEGIS-061 and AEGIS-237 share infrastructure?** They share a *contract*, not a *mechanism*, and forcing them into one system would be dishonest:

- **061 / 070** is *in-stream* recovery: a gap is detected mid-feed, deltas are buffered, a fresh **market-data snapshot message** re-bases the book, buffered deltas replay onto it. The artifact is a wire message.
- **237** is *process-boundary* recovery: a byte-stable **file snapshot** of OMS + portfolio state, restored into a fresh process, verified by round trip and continuation equality — exactly mirroring `ExchangeSnapshot` (ADR-0013).

They share the five obligations of `docs/RECOVERY_CONTRACT.md` (state ownership, versioned payload, byte stability, round-trip verification, defined shutdown) and one serialization discipline. They are mapped to **independent tests and independent evidence**, and neither is claimed from the other's proof.

**Not M3** — do not reopen: AEGIS-024→M4, AEGIS-059→M9, AEGIS-062→M5, AEGIS-063→M5. AEGIS-238 (M5) also notes execution latency arrives with M3; that is M5's row, not a debt M3 discharges.

Within M3 the gate authorises the path, not the diff — so the enumerated `reason` above is the review contract the owner reads PR-B against and the independent spec-auditor checks the diff against at closure. Narrowing that further would require a new mechanism (digest pinning, per-diff approval), which is out of bounds: **R8 is not redesigned.**

## 6. ARCHITECTURE

### Preserved without exception

M1 matching/FIFO/cancel/modify semantics (ADR-0011) are untouched. `cpp/exchange/matching` and `cpp/exchange/sequencer` are read-only for M3. `cpp/replay`'s boundary is preserved: `ReplayEvent` stays identity/ordering only and `DeterministicFaultInjector` is not modified — M3 *consumes* it. No wall clock on any deterministic path; the participant runs on `VirtualClock` / injected `common::WallClock`. Recovery uses explicit persisted state and cursors, never elapsed real time.

### Six decisions that define M3

**(a) Market-data vocabulary lives in `cpp/events`, published by `cpp/exchange/market_data`.**
`cpp/events/envelope.hpp` reserves `1..999` for exchange-side domain messages (10-15 used) and `1000..1999` for participant-side. Depth snapshots and incremental updates are exchange-**published**, so they take permanent numbers in the exchange band (20+). ADR-0009's rationale applies unchanged: they live in `cpp/events` so the participant decodes them **without depending on the exchange layer**.

`cpp/exchange/market_data` derives snapshots and incrementals from the order book plus the existing `EmittedEvent` stream. It **observes**; it is never called from `MatchingEngine` and cannot alter emitted-event order.

**(b) A participant composition root: new layer `cpp-participant-app`.**
Today nothing may legally see feed + book + stats + OMS + portfolio at once, yet AEGIS-109/114 ("integration tests reconcile fills and positions") and AEGIS-237 require exactly that. This mirrors `cpp-exchange-app` precedent verbatim ("The composition root: nothing else may legally see all of sequencer, book, matching and state at once", ADR-0012). It also provides `aegis_participant_run`, the deterministic CLI that evidence generators drive — matching `aegis_exchange_replay` (M1) and `aegis_replay_run` (M2). It is the only layer permitted to depend on `cpp-replay`, which is how AEGIS-060/061 fault scenarios reach the participant.

**(c) The OMS declares its own inputs; it does not reach backwards.**
`cpp-participant-oms` may depend only on `[cpp-common, cpp-events, cpp-participant-risk]`, and risk is M5/empty. So at M3 the OMS sees only `cpp/common` and `cpp/events`. AEGIS-110/115 need queue and market state — the OMS therefore **declares narrow input types in its own headers** (`MarketView`, `QueueEstimate`) and the app layer adapts book-builder output into them. **`may_depend_on` for the OMS is not widened.**

**(d) The risk seam is mandatory and empty.**
AEGIS-108's frozen state list includes `RiskPending`. M3 delivers a `RiskGate` interface **declared by the OMS** and a state machine in which no order can reach `Submitted` without a `RiskDecision` — the seam that AEGIS-120 (M5) later fills. **No risk policy, no limits, no kill switch is implemented at M3.** The only M3 implementation is a test/app-supplied decision source, explicitly named as such. This is an interface for a later milestone, not its business logic.

**(e) Two recovery mechanisms, one contract.** As set out in §3.

**(f) AEGIS-119 — the adapter boundary is a *message* boundary.**
MASTER_SPEC immutable principle 1: *"Exchange simulation and proprietary-trading participant logic are separate systems connected only by versioned messages."* No participant library may hold a code edge to the exchange — so no production adapter may name `ExchangeNode`.

*The interface.* `cpp/participant/oms/execution_adapter.hpp`, owned by `cpp-participant-oms`, defined **purely over `cpp/events` types**: `NewOrderCommand` / `CancelOrderCommand` / `ModifyOrderCommand` out, decoded `OrderAccepted` / `Rejected` / `Modified` / `Replaced` / `Trade` / `Terminated` in, on an injected clock. It names no exchange type. That is what "environment-independent" in AEGIS-119's own title means, and it is exactly ADR-0009's reason for putting the vocabulary in `cpp/events`.

*The two production implementations, both wholly inside the participant architecture:*

| | **`TransportExecutionAdapter`** | **`RecordedResponseAdapter`** |
|---|---|---|
| **Purpose** | The environment-independent path: encodes OMS intent to `Envelope`s, hands them to an injected `ExecutionTransport`, decodes whatever comes back. The seam M9's paper transport later fills. | Drive the OMS through response sequences no matching engine can be made to emit on demand — cancel/amend races, rejection paths, partial-fill ladders. |
| **Response provenance** | Arrives asynchronously from outside, with modelled latency (AEGIS-113). The adapter **owns no responses** and cannot predict them. | Fully determined at construction from a committed fixture script. The adapter **owns its responses**; no transport exists. |
| **Distinct failure modes** | Transport failure, response arriving after a local cancel, unmatched correlation. | Script exhaustion, script/scenario mismatch. |
| **Why not M9** | Opens no socket, speaks no broker protocol, holds no credential, has no session/reconnect logic, reconciles against no external account. It is a transport *seam*, not a transport. | Same, and it does not even have a seam — it is a fixture reader. |

Both headers live in `cpp/participant/oms/`, the sole layer with `allows_gateway_adapters: true`. **`cpp-participant-oms.may_depend_on` is unchanged (`[cpp-common, cpp-events, cpp-participant-risk]`), and no new edge of any kind is required — the `m3-architecture-transition` four-change set stands untouched.**

*Where the real M1 exchange meets the participant: two legal boundaries, neither a code edge.*

1. **Stream boundary (evidence + reconstruction).** `aegis_exchange_replay` writes the canonical event log and market-data stream; `aegis_participant_run` reads it. Two processes, versioned messages, zero shared code — the boundary M2 already uses (`tests/replay/test_exchange_determinism.py` drives `--snapshot-out`/`--restore-from` across a process boundary). Carries AEGIS-064–070, 060/061 and 237 evidence.
2. **Integration harness (interactive execution).** `tests/` is **outside `covered_roots`** (`configs/architecture_rules.yaml`), so a harness in `tests/cpp/unit/test_participant_exchange_integration.cpp` may legally construct a real `ExchangeNode` and a real participant stack and implement `ExecutionTransport` over the exchange's command/event interface. It is the **only** code that sees both sides; it creates no production dependency; it exercises **real M1 FIFO matching, unmodified**. Precedent: M2's `tests/cpp/unit/test_replay_full_stack_integration.cpp` lives in the unit binary for exactly this reason.

The frozen acceptance criteria for AEGIS-109 (`Integration tests reconcile fills and positions`) and AEGIS-114 (`Position/cash reconciliation passes`) ask for integration tests. The harness is what the criterion requests, not a workaround for one.

*Evidence discipline.* `RecordedResponseAdapter` is never the sole proof of an execution requirement. AEGIS-109/110/111/114 are proven through `TransportExecutionAdapter` with the harness transport driving the **real matching engine**; `RecordedResponseAdapter` contributes race and rejection shapes for AEGIS-112 and the cross-adapter equivalence for AEGIS-119. Every artifact's `not_evidence_for` states that M3 ships a transport seam and no transport implementation — paper connectivity, restart recovery and broker reconciliation remain AEGIS-221/222 at M9.

### Deliberately not advanced

No strategy (M4), no risk engine (M5), no stat-arb (M6), no decision intelligence (M7), no `cpp/memory` or `cpp/queues` (M8 — denied in M3 scope), no paper/live adapter or transport implementation (M9).

**`cpp-statistics` is a generic library, not a participant component.** Its declared dependency is narrowed to `[cpp-common]`. It implements AEGIS-098–107 over plain numeric observations (`double`, `int64`, typed durations) and has no knowledge of books, orders, feeds or participants — so M4 strategies, M5 risk, M6 attribution and M7 decision intelligence can reuse it without inheriting participant-domain types. Statistics never reaches backwards into the book, and no compensating `book-builder -> statistics` edge is added in the other direction either: **the app layer is the only place the two meet.**

The layer keeps its declared namespace `aegis::participant::stats` — renaming it is not authorised by `m3-architecture-transition` and is not needed for the decoupling.

Edges deliberately **absent**: statistics→book, book→statistics, OMS→book, OMS→statistics, portfolio→OMS, statistics→OMS, feed-handler→replay, **any participant→exchange edge (including `cpp-participant-app`→`cpp-exchange-*`)**, any exchange→participant edge. Portfolio changes only from decoded execution/account events (ARCHITECTURE rule 5). The exchange and the participant meet only through versioned messages, at the two boundaries in §6(f) — a process/stream boundary and a test-only integration harness, neither of which is a code edge.

**Where composition happens.** Book/feed components produce numeric observations; the app layer feeds them into `cpp-statistics` and routes the results. Concretely for the two requirements this affects:

- **AEGIS-074 (trade/cancellation intensity)** — `cpp-participant-book-builder` extracts trade and cancellation *events and counts* from the reconstructed stream (participant-domain work); `cpp-statistics` provides the generic rolling-rate estimator (numeric work); `cpp-participant-app` composes them. The frozen acceptance ("online/offline equivalence tests pass") is exercised on the composed path, with the estimator additionally covered by its own generic tests against the Python reference.
- **AEGIS-075 (queue depletion and adverse selection)** — stays entirely in `cpp-participant-book-builder`: queue depletion and post-fill adverse-selection windows are participant-domain concepts and are **not** moved into `cpp-statistics`. Where a generic rolling window is genuinely needed, the app layer supplies the estimator's output rather than the book builder importing it.

CMake targets follow the enforced convention: `aegis_exchange_market_data`, `aegis_participant_feed_handler`, `aegis_participant_book_builder`, `aegis_statistics`, `aegis_participant_oms`, `aegis_participant_portfolio`, `aegis_participant_app`. New `cpp/participant/CMakeLists.txt`, `cpp/statistics/CMakeLists.txt`, per-layer files, plus `add_subdirectory` entries in `cpp/CMakeLists.txt`.
